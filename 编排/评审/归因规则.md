# 归因规则：是用的人的问题，还是工具的问题

拆拍台是**引导工具**。用的人用错了，大多数时候本身就是工具没引导到位。所以：

**默认推定是工具的问题。** 只有满足下面「用户问题」的全部条件，才能归给用户。

## 对判定书里的每一个阻塞问题，查三件事

1. **页面当时有没有提示？** 对应的格子旁边有没有说明（「?」）、提示文字、警告？说明里讲没讲到这一点？
2. **检查页报没报？** 看本轮 `检查.md`：这个问题对应的位置，有没有「缺」或「警」？
3. **A 当时看到了什么、为什么这么填？** 查 A 的卡顿日志；日志里没有的，追问 A（接回同一个 A）。**只问事实**：当时屏幕上有什么、你点开过说明吗、你为什么这么填。不问「是不是你的问题」。

## 归类

| 情况 | 归类 |
|---|---|
| 工具没有任何提示，检查也是绿的 | **工具：缺引导＋缺检查** |
| 说明里讲了，但检查没报 | **工具：缺检查**（引导工具不能指望人记住说明） |
| 检查报了，但 A 没看见或没看懂 | **工具：提示不显眼 / 说不清** |
| 数据结构里根本没地方写这个信息 | **工具：缺结构**（这种最要紧——下游要的信息，工具没给位置） |
| 工具让填的东西彼此打架、顺序有环 | **工具：方法问题**（回到方法层面审，不是补个字段能解决的） |
| 工具明确警告了、检查也报了、A 日志显示看到了，仍然无视 | **用户问题** |
| 同一处连续两轮都被不同的 A 无视 | 改判 **工具：提示不显眼** |
| 故事本身在这里就没说清 | **故事问题**（不改工具；记下来告诉制作人） |

## 归因表格式（`归因.md`）

| # | 阻塞问题 | 页面有提示吗 | 检查报了吗 | A 当时看到什么 / 为什么这么填 | 归类 | 处置 |
|---|---|---|---|---|---|---|

「引导问题」（判定书第四节）也逐条列进来，处置写「改」或「不改：理由」。

## 修的时候

- 先问：能不能**不加字段**解决？（改顺序、改说明、改检查、改默认值、把两个格子并成一个。）
- 必须加字段的，在 `修复.md` 里写理由，并记录字段预算的变化。
- 一个问题指向「方法问题」的，停下来先对齐方法，不要打补丁。
