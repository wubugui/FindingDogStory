# 拆拍台评审流程

目的：反复检验拆拍台是不是真的做到了它该做的事——**把一段故事梗概，引导人拆成能直接交给别人落地、且落地出来还是原来那个故事的结构化数据**。
不是测功能有没有 bug（那个开发时自己测），是测结果。

## 角色

| 角色 | 是谁 | 能看到什么 | 产出 |
|---|---|---|---|
| A 作者 | 只懂自己故事的人，第一次用拆拍台 | 故事原文、自己已经想好的玩法清单、浏览器里的拆拍台页面（只能看屏幕上有的） | 拆分结果（页面里的数据）＋ 卡顿日志 |
| B1 复述 | 没看过原故事的人 | 只有拆分结果（去掉梗概原文和原文摘句） | 把故事复述出来 |
| B2 落地试做 | 下游真正要把它做进游戏的人 | 只有拆分结果 ＋ 游戏仓库的落地方法文档 | 落地草稿 ＋ **猜测清单**（结果里没写、只能猜的地方） |
| B 判定 | 评委 | 原故事、B1 的复述、B2 的猜测清单、机器检查、A 的卡顿日志、评分标准 | 通过 / 不通过 ＋ 阻塞问题清单 |
| 开发 | 拆拍台的开发 agent（也是流程的调度者） | 全部 | 归因表、修复、下一轮 |

A 每一轮都是全新的（保证不知情）；追问时接回同一个 A。B1、B2 互相不通气，可以同时跑。

## 一轮怎么跑

1. 开发：建 `轮次/<故事>-第N轮/`，起本轮服务（新端口＝干净的浏览器存储）：`node 编排/评审/服务.cjs <端口> <轮次目录>`。给 A 的 URL 带 `?full=1`（页面缺省是简单模式，只有大纲、详情、梗概、停车场；评审测的是九步完整模式）。
2. **A** 按 `角色/A-作者.md` ＋ `故事/<故事>.md` 用页面拆故事，写 `A-卡顿日志.md`，做完不关标签页。
3. 开发：在 A 的标签页里把数据存到轮次目录（`A-结果.json`），跑 `node 编排/评审/导出.cjs <轮次目录>`，得到 `拆分结果.md`（已去掉原文）、`检查.md`、`度量.json`。
4. **B1**、**B2** 同时跑，分别写 `B1-复述.md`、`B2-落地试做.md`。
5. **B 判定** 按 `评分标准.md` 写 `B-判定.md`。
6. 通过 → 这个故事收工。不通过 → 开发按 `归因规则.md` 给每个阻塞问题归因（需要时追问 A：当时屏幕上看到什么、为什么这么填——只问事实，不让 A 下结论），写 `归因.md`。
7. 归为工具问题的 → 开发改工具，写 `修复.md`（改了什么、字段预算和操作步数涨没涨、涨了为什么）。然后换一个全新的 A 跑下一轮。

## 硬规矩

- **评分标准冻结。** 迭代期间不改 `评分标准.md`；要改得制作人点头。免得开发迎合评委。
- **只有阻塞问题才打回。** 不阻塞的记下来，不为它改工具。
- **不许越改越复杂。** 每轮记录字段预算（`度量.json` 的 `fieldBudget`）和 A 的操作步数；修复让这两个数上涨的，`修复.md` 里必须写理由。
- **每个故事最多 4 轮。** 4 轮还不过，停下来报告制作人，不硬磨。
- **留出的故事不参与迭代**，只在另外两个都通过之后验一次。
- 工具里不出现任何引擎、技术概念；但 B2 是懂技术的下游，它用什么方法落地是它的事。

## 这个流程证明不了什么

- **玩法好不好玩**：得靠成品切片给真人试。
- **制作人用起来累不累**：A 是 LLM，不嫌烦、不卡壳。所以 A 的卡顿日志每个大版本要给制作人翻一眼——它卡的地方，多半人也会卡。
